# 评估集方向标注规范

> 本文件是 `all_cases.json` 中 `expected_direction` 字段的统一标注标准。
> 凡新增或修改评估集条目，必须严格遵循本规范。

---

## 一、角色

你是一个严格但不死板的审核员。任务是复核职位描述的 `expected_direction` 标注。

---

## 二、核心铁律

每个职位必须且只能分配一个方向。绝不允许一条 JD 同时拥有两个方向标签，也不允许"斜杠"标注。

---

## 三、最高判断原则：方向判定总纲

`expected_direction` 只回答一个问题：**这个岗位实际在做什么、产出什么、服务哪个业务。**
它衡量的是岗位的业务方向，不是岗位需要的技能画像。

判断的根本，不是看 JD 用了什么技能或技术栈（AI、后端、数据、平台都只是"怎么做"），而是看这个岗位要产出什么成果、该成果属于哪个领域。判定时连问三层：

1. 这个岗位的主导产出 / 交付物是什么？
2. 该产出服务的业务领域是什么？
3. 成果落在哪个领域，方向就归哪个领域。

### 三条"≠"铁律

- **技能 ≠ 方向**：出现某项技能要求，不能直接推出方向，必须回查主导产出。
- **公司 ≠ 方向**：在某领域公司上班，不能直接推出这个岗就做该领域，必须回查主导产出。
- **关键词 ≠ 方向**：JD 里出现某个词，不能直接推出在做某事，必须回查它是不是主导产出。

### "≠"的正确理解

"≠"攻击的是推理路径，不是结论。它要禁止的是"看到信号 X → 直接盖章方向 Y"这种捷径。合法的箭头永远只有一条：**看主导产出 → 定方向**。

逐条配例：
- 技能 ≠ 方向：
  - "会 Solidity / 懂智能合约"若只是加分项，而主导产出在链下 → 不归 web3，归 technical；
  - 但若主导产出本身就是写合约 / 链上逻辑 → 就是 web3。
  - "用了 AI"不自动归 technical：支付公司反欺诈岗天天用 AI，但主导产出是支付风控系统 → payment（AI 只是手段）。
- 公司 ≠ 方向：
  - Web3 交易所招"行政 IT 运维"（修员工电脑、维护办公网络），主导产出是内部办公支撑 → technical / default，不归 web3。
- 关键词 ≠ 方向：
  - crypto 公司招后端，JD 提一句"支持数字资产 payment gateway 等场景"，但主导产出是钱包和智能合约 → 归 web3，payment 仅作背景。

### 「产出本身是领域产物」vs「通用产出被领域使用」

- **产出本身就是该领域的技术产物**：写链上合约、建清结算/对账系统、实现钱包/DeFi/撮合/支付路由逻辑。删掉这个领域，岗位的产出就不存在了 → 归该领域。
- **产出是通用技术件，只是被该领域使用**：通用 AI agent 平台 / 内部效率工具 / 通用数据 / DevOps / 平台基建。删掉这个领域，这个通用平台照样成立 → 归 technical。

**判据**：「让某业务线更高效」≠「产出该业务线的技术产物」。

---

## 四、主判断流程（严格按顺序执行）

### 1. 【定位优先】面向客户 → solutions

先判断岗位核心定位是否"面向客户 / 为客户服务"。若是——为客户做方案、集成、售前、咨询、实施，或客户成功、客户经理、客户关系维护——**直接判 solutions**。此判定优先于下方一切规则。

### 2. 【成果定方向】锁定主导产出

若不符合 solutions，则锁定主导产出及其服务的业务领域，落在 web3 / payment / technical / default 中的哪一个。

### 3. 【兜底归类】

- 通用技术产出 → **technical**
- 通用非技术产出 → **default**

### 4. 【平局裁决，仅作兜底】

当且仅当两个方向势均力敌时，按优先级链：**payment > web3 > technical > default**

- solutions 已在第 1 步处理，不入此链。
- 一方若只是背景提及 / 加分项，绝不构成平局。
- payment 参与平局前必须先过 payment 闸门。

## 五、五类方向语义定义

### web3

主导产出直接与区块链、加密货币、去中心化应用相关。典型特征：智能合约、链上交易、钱包、DeFi、NFT、WaaS、EVM、Solidity、链上数据、共识机制等。

若岗位只是"在 Web3 公司写纯通用后端 / 前端 / 平台、产出不触及任何链上业务逻辑"，不归 web3（B 类，归 technical）。

### payment

主导产出围绕支付、清结算、账务、对账、收单、代付、钱包即服务、SWIFT、FPS、支付通道。

**payment 闸门（硬性前置）**：只有当主导产出本身就是一套真实的支付/清结算系统时才归 payment。锚点：清结算/settlement、对账/reconciliation、收单/acquiring、商户结算、交易流水、支付路由、费率计算、备付金、payment rails。

反例：crypto/web3 公司把"payment gateway"作为众多用例之一带过，主导产出是区块链系统 → 归 web3。

加密货币支付：若主导产出是支付清结算链路 → payment；若主导产出是编写/交互链上智能合约本身 → web3。

### solutions

角色核心定位是"为客户服务"。涵盖：解决方案工程师、方案设计、系统集成、售前、技术顾问、客户成功、客户经理、客户关系维护、客户实施等。

solutions 与 technical 的分水岭：**工作对象是不是客户**。同样写代码，为内部产品写 = technical，为某个客户做定制集成/POC = solutions。

### technical

纯技术开发/运维/测试/数据工程岗，且主导产出不属于以上三类、不服务任何特定业务领域。

通用技术平台/工具/基础设施（含 AI agent 平台、内部效率工具、通用数据/平台基建），即便服务对象身处 web3/payment 领域、即便雇主是领域巨头，只要该平台本身不实现链上/支付业务逻辑（B 类），一律归 technical。

### default

无法明确归入以上四类的通用职能岗。

**非工程岗两分法**：
- **领域无关支撑岗**：放到任何行业都长一样（HR、财务、行政、法务、市场/运营）→ default，置信度 high。
- **领域主题型非工程岗**：名号挂了某领域（如 Web3 管培生、crypto BD），但实际产出仍是通用职能产物 → default，置信度 borderline。

判据：领域是它的"包装/背景"，还是它的"实际产出"？

凡面向/服务客户、维护客户关系的岗位归 solutions，不进 default。

---

## 六、加分项/nice-to-have 的判定

核心原则：判定看"岗位的主导产出本身是否就在该领域里产出"，而非技能被写成 required 还是 nice-to-have。

三种情况：
1. **同方向内技能扩散**：不跨方向，不拆分。
2. **不相关领域的加分项**：不计入方向判断。
3. **相辅相成领域的加分项**：计入，问"主导产出是不是就在这个领域里产出？"

**反向硬信号**：若一个号称服务于某领域的技术岗，其全部技能要求里完全没有该领域的任何技术技能 → B 类强证据 → 归 technical。

---

## 七、公司业务信号与领域穿透

### 通用/多元化公司

公司名信息量小，不可反推方向。必须读 JD 主导产出。

### 领域巨头推定（降级为兜底）

仅当 JD 连 A/B 类都无法判别时才用。凡靠巨头推定裁出的方向，置信度强制 borderline。

### 穿透硬标准：A 类 / B 类判别

**先问一刀**："该岗主导产出，是该领域的技术实现本身，还是一套被该领域使用的通用件？"

- **A 类**（产出即领域产物 → 穿透至 web3/payment，可 high）
- **B 类**（通用件被领域调用 → 不穿透，归 technical）

**两个 B 类强信号**（命中其一即高度怀疑 B 类）：
1. 该领域在 JD 里只是"多个并列服务对象之一"（如 "and beyond"）
2. JD 的技能要求里完全没有该领域的技术技能

**巨头处的特例**：A/B 难分时 → technical，borderline。

---

## 八、置信度定义

- **high**：多个信号收敛，未动用任何翻盘性规则。
- **borderline**：靠平局链、default 回落、巨头推定、定位优先覆盖裁出；或表面信号打架；或存在未采纳的穿透诱惑。

**强制 borderline 的情况**：
- 靠巨头推定裁出的 web3/payment
- 靠平局链裁决
- 领域主题型非工程岗归 default
- 靠定位优先强行覆盖技术赛道归 solutions（岗位身处 payment/web3 等技术赛道时）
- B 类通用平台身处领域巨头，存在未采纳的穿透诱惑

---

## 九、参考边界案例

- "加密货币支付后端，主导清结算链路" → payment
- "区块链应用后端，主要做智能合约交互" → web3
- "crypto 公司把 'payment gateway' 作为众多用例之一带过，主导产出是 dApp/智能合约" → web3
- "巨头的 AI/后端/数据岗，主导产出是加密交易/清算/链上系统的实现（A 类）" → web3，high
- "巨头的通用 AI Agent 平台 / 内部效率工具岗，被 trading、compliance、risk 等多条业务线（and beyond）使用、技能要求零区块链（B 类）" → technical，borderline
- "巨头 AI 平台岗，连 A/B 类都读不出、仅靠'它是币安'默认归口" → web3，borderline
- "通用公司的 AI Agent 平台（B 类）" → technical
- "巨头内部办公 IT 运维/HR 系统维护" → technical/default（推翻巨头推定）
- "后端岗，职责就是为链上系统写后端，web3 知识仅写作'加分'" → web3（产出在链上，A 类）
- "招后端，前端/CI-CD 为加分，无 web3/payment 业务" → technical
- "Web3 公司的管培生/crypto BD，产出通用管理/商务" → default，borderline
- "支付公司数据中台，不碰支付业务" → technical 或 default
- "支付/区块链公司的售前/方案工程师" → solutions
- "区块链公司客户成功经理" → solutions
- "支付公司产品经理，成果非技术产物" → default
